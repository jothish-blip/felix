1. SYSTEM INTRODUCTION & CORE MISSION
====================================================================================================
FELIX v3.0 is an autonomous, open-source vulnerability assessment and penetration testing (VAPT)
engine written in pure Go.

The core mission of FELIX v3.0 is to provide a single, unified security testing platform that
eliminates the fragmentation between dynamic web vulnerability scanners (DAST), software composition
analysis (SCA), cloud security posture assessment (CloudSec), and mobile application security (MAST).

Core Engineering Directives:
1. Complete Surface Discovery: No application surface is ignored due to frontend JavaScript frameworks.
   Every Single-Page Application (Angular, React, Vue, Next.js) must have its DOM fully evaluated.
2. Context-Aware Vulnerability Fuzzing: Fuzzing algorithms must understand where input parameters land
   (HTML body, attribute, SQL query, shell command, file path) and apply differential response logic.
3. Multi-Persona Authorization Auditing: BOLA/IDOR/BFLA flaws cannot be proved with a single session;
   FELIX must coordinate multiple authenticated personas (User A, User B, Admin) concurrently.
4. Comprehensive CVE Coverage via Open Data: Rather than attempting to manually author hundreds of
   thousands of signatures from scratch, FELIX ingests the authoritative National Vulnerability
   Database (NVD), Google Open Source Vulnerabilities (OSV), and GitHub Security Advisories into an
   embedded SQLite engine, and executes community-standard YAML templates via Go bytecode closures.
5. Zero False-Alarm Verification: No finding is reported based purely on an error regex. Every flaw must
   pass deterministic, non-destructive secondary proof (Boolean differential, canary reflection, or OAST).
6. Multi-Hop Attack Chaining: Findings are not presented as disconnected rows; they are modeled in a
   directed acyclic graph (DAG) to synthesize full breach paths with reproducible reproduction steps.
7. Exact Remediation Diffs: Every confirmed finding includes code-level patches (parameterized queries,
   sanitization routines, configuration blocks) rather than generic text.

To understand why users will adopt FELIX over existing tools, we must look at what the industry giants

----------------------------------------------------------------------------------------------------
A. SNYK (Valuation: $7B+ | Focus: SCA, Container & Static Analysis)
----------------------------------------------------------------------------------------------------
What Snyk Does Well:
- Massive proprietary software vulnerability database.
- Seamless IDE integration and dependency pull-request fixes.
- Strong developer-centric brand recognition.

What Snyk FAILED to Solve (The Glaring Weakness):
- Snyk is almost entirely STATIC. It scans code repositories and package-lock files.
- It cannot test a RUNNING, live web application or API dynamically (DAST).
- It is completely blind to runtime authorization bypasses: Snyk will never detect BOLA/IDOR because
  BOLA exists in application database logic, not in an outdated npm library.
- Snyk suffers from massive "Alert Fatigue": it flags thousands of vulnerable functions that are imported
  in a library but never actually invoked by the application code (unreachable dependencies).

How FELIX Solves It:
- FELIX evaluates LIVE, running applications dynamically at runtime.
- FELIX verifies whether an endpoint or vulnerable library is actually reachable and exposed over the wire.
- FELIX tests live authorization boundaries across multiple authenticated sessions (BOLA/IDOR).

----------------------------------------------------------------------------------------------------
B. PROJECTDISCOVERY NUCLEI (High-Growth Open-Source Scanner)
----------------------------------------------------------------------------------------------------
What Nuclei Does Well:
- Extremely fast stateless YAML template matching.
- Massive, vibrant open-source community that writes templates for newly dropped CVEs.
- Clean Go CLI architecture.

What Nuclei FAILED to Solve (The Glaring Weakness):
- Nuclei is fundamentally STATELESS. It sends one-shot HTTP requests.
- It has no native dynamic browser engine: it cannot execute JavaScript, click buttons, or render
  Single-Page Applications (Angular, React, Vue). It is blind to dynamically rendered routes.
- It cannot maintain stateful multi-step user sessions: it cannot log in via multi-step forms, refresh
  session tokens when expired, or handle dynamic CSRF nonces across sequential requests.
- It cannot test BOLA/IDOR matrices (User A vs. User B).
- Findings are output as isolated flat lines without attack-chain correlation or code diffs.

How FELIX Solves It:
- FELIX integrates Headless Chromium (CDP) to render complex SPAs, simulate clicks, and sniff APIs.
- FELIX maintains a stateful session state machine with automatic keep-alive and anti-CSRF sync.
- FELIX maintains dual-user personas to autonomously prove BOLA/IDOR.
- FELIX correlates findings into multi-hop breach graphs with deterministic proof commands.

4. HIGH-LEVEL ARCHITECTURAL DESIGN (THE 7 CORE ENGINES)
====================================================================================================
The system is partitioned into seven loosely-coupled, strictly-bounded Go packages:

[ENGINE 1: Dynamic Chromium Execution & SPA Crawler] (`pkg/crawler/browser`)
- Pure Go Chrome DevTools Protocol (CDP) client using `chromedp`.
- Controls headless Microsoft Edge (`msedge.exe`) or Google Chrome (`chrome.exe`).
- Discovers routes, renders client-side DOMs, dispatches synthetic user events, and sniffs network calls.

[ENGINE 2: Context-Aware Injection & Parameter Fuzzer] (`pkg/fuzzer`)
- Extracts parameters across query strings, JSON payloads, multipart forms, and headers.
- Implements differential response algorithms for SQLi, XSS, SSRF, Path Traversal, and Command Injection.

[ENGINE 3: Multi-Persona State Machine & BOLA Prover] (`pkg/auth/persona`)
- Manages multi-step login macros, session keep-alive loops, and dynamic CSRF nonce tracking.
- Orchestrates multi-tenant token swapping (User A vs. User B) to prove BOLA (OWASP API1:2023).

[ENGINE 4: 300,000+ Software CVE Intelligence Engine] (`pkg/cve`)
- Embedded SQLite store indexing NVD, OSV, and GitHub Security Advisories.
- Extracts Common Platform Enumeration (CPE) fingerprints and runs compiled YAML vulnerability templates.
- Houses an Out-of-Band (OAST) DNS/HTTP callback listener for blind vulnerability confirmation.

[ENGINE 5: Cloud-Native & CloudSec Penetration Subsystem] (`pkg/cloudsec`)
- Assesses cloud metadata endpoints (AWS IMDSv1/v2, GCP, Azure), public storage buckets, and K8s APIs.
- Evaluates IAM privilege escalation paths and container socket exposures.

[ENGINE 6: Mobile Application Dynamic & Static Analysis Subsystem] (`pkg/mobile`)
- Static manifest, permission, secret, and bytecode decompiler for Android APKs and iOS IPAs.
- Dynamic runtime bridge interfacing with Frida and ADB for SSL pinning bypass and IPC fuzzing.

[ENGINE 7: Autonomous Multi-Hop Attack-Chain & Proof Synthesizer] (`pkg/correlation`)
- Directed Acyclic Graph (DAG) risk correlator that connects isolated vulnerabilities into attack paths.
- Generates deterministic `curl` commands, reproduction scripts, and code remediation diffs.

Goal:
Equip FELIX with an active injection engine capable of testing all input vectors for critical web
vulnerabilities using differential response analysis, error verification, and time-delay analysis.

Objectives:
1. Extract and categorize every parameter vector (Query, JSON body, Form data, Headers, Path variables).
2. Implement Boolean, Error-based, and Time-based differential SQL Injection verification.
3. Implement Cross-Site Scripting (XSS) context-aware reflection analysis (HTML, Attribute, Script block).
4. Implement Path Traversal, Local File Inclusion (LFI), and Arbitrary File Read verification.
5. Implement Command Injection (OS RCE) and Server-Side Template Injection (SSTI) verification.

Strategy:
Avoid blind regex matching. Use differential response algorithms: send a baseline request, a truth-condition
request, and a false-condition request, calculating Levenshtein distance, word count, and status code deltas.

Implementation Plan:
Step 2.1: Intelligent Parameter Extractor (`pkg/fuzzer/extractor.go`)
- Parse URL query strings, JSON request trees, XML payloads, multipart form-data, and custom headers.
- Extract parameter context: Numeric, Alphanumeric string, Email, UUID, File path, Base64 blob.
- Generate mutation candidate targets for each parameter while holding non-targeted fields constant.
* Testing Verification Target : `C:\SecurityLabs\webgoat` (Lesson 1-5), `nodegoat` (:4000), `dvga` (:5013)
* Required Evidence Receipt   : `test/evidence/phase2/2.1_param_extraction_proof.json`
* Iron Gate Exit Condition    : Advancement to Step 2.2 is BLOCKED until 100% parameter extraction accuracy.

Step 2.2: SQL Injection Differential Engine (`pkg/fuzzer/sqli.go`)
- Boolean Differential Analysis with Dynamic Content Masking:
  * Dynamic Masking: Send two identical baseline requests (`Baseline_1` and `Baseline_2`) prior to fuzzing.
    Diff them to identify and mask naturally changing elements (timestamps, rotating CSRF tokens, session IDs).
  * True condition: `param=val' AND 1=1--` (or `param=val AND 1=1`)
  * False condition: `param=val' AND 1=2--` (or `param=val AND 1=2`)
  * Calculate similarity index: True condition must match baseline; False condition must differ, evaluating
    Levenshtein distance and DOM structure exclusively against the masked stable DOM skeleton.
- Database Error Signature Matching: Check for dialect-specific syntax errors (MySQL, PostgreSQL, MSSQL,
  Oracle, SQLite) without flagging generic framework errors.
- Sequential Mathematical Progression for Time-Based Latency Verification:
  * Rather than relying on a single static 5s threshold, execute sequential probes: `sleep 1s` -> `sleep 3s` -> `0s control`.
  * Require round-trip response times to scale strictly linearly with commanded delays while control probe matches baseline,
    eliminating concurrency-induced latency false positives on single-threaded test runtimes.
