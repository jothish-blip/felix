[L1.1] Anti-Bot WAF & Browser Fingerprint Detection Wall (Cloudflare / Akamai / Turnstile)
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/launcher.go` (Chromium Launch Flags)
Current Behavior    : Launches headless Microsoft Edge or Google Chrome using standard CLI flags:
                      `--headless`, `--disable-gpu`, `--no-sandbox`, `--disable-dev-shm-usage`.
The Limitation      : Chromium in default `--headless` mode exposes obvious automation artifacts:
                      - `navigator.webdriver === true` in JavaScript global window context.
                      - Missing `window.chrome.runtime` and empty `navigator.plugins` array.
                      - WebGL vendor strings report `Google SwiftShader` or `Mesa OffScreen`.
                      - Anomalous User-Agent and CDP `Runtime.enable` leak hooks.
Upstream Impact     : In Phases 2 and 8, when FELIX targets enterprise applications or modern SaaS
                      protected by Cloudflare Bot Management, Akamai Bot Manager, Cloudflare Turnstile,
                      or AWS WAF Captcha, the browser is instantly greeted with an HTTP 403 Forbidden
                      or an interactive JavaScript challenge wall. The crawler is completely blocked
                      at the gateway, preventing all downstream parameter extraction, active fuzzing,
                      and vulnerability discovery.
Planned Fix Phase   : Phase 8.3 / Subphase 1.1 Maintenance (Stealth CDP Profile Injection)
Remediation Design  : Inject pure Go CDP overrides via `Page.addScriptToEvaluateOnNewDocument`:
                      - Redefine `Object.defineProperty(navigator, 'webdriver', {get: () => undefined})`.
                      - Mock realistic `navigator.plugins`, `navigator.languages`, and hardware concurrency.
                      - Spoof WebGL vendor/renderer strings to match native host GPU drivers.
                      - Route CDP commands through a stealth WebSocket proxy that strips automation markers.
Testing Verification:
- Designated Target : `C:\SecurityLabs\juice-shop` (Port 3000) behind simulated WAF challenge fixture:
                      `test/lab/waf_challenge.html` & online benchmark `https://bot.sannysoft.com`.
- Testing Procedure : Direct `pkg/crawler/browser` launcher to `waf_challenge.html`. Evaluate whether
                      the bot detection script identifies automation flags.
- Pass Exit Metric  : 100% of bot detection checks report "PASS" (`navigator.webdriver` undetected);
                      crawler successfully navigates past challenge wall without manual intervention.

[L1.2] Decoupled Session Lifecycle & Accidental Logout State Loss During Traversal
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/monkey.go`, `pkg/crawler/browser/spa.go`
Current Behavior    : DOM Monkey clicks links, buttons, and form submits across the DOM tree. While it
                      avoids explicit destructive keywords ("delete", "remove"), it does not understand
                      session semantics.
The Limitation      : In modern authenticated SPAs, navigation menus frequently contain "Log Out",
                      "Sign Out", "Switch Account", or idle session expiration timeouts (e.g. 15-minute JWTs).
                      If the crawler clicks a logout trigger or the session token expires mid-crawl:
                      - The browser state transitions back to the unauthenticated login screen.
                      - The browser crawler continues traversing, but all discovered endpoints are now public.
Upstream Impact     : In Phase 2 (Active Parameter Fuzzing) and Phase 3 (Multi-Persona BOLA), if the session
                      drops out, all subsequent active injection probes execute unauthenticated. The scanner
                      silently registers false negatives, assuming protected endpoints are properly secured,
                      when in reality the session was simply lost.
Planned Fix Phase   : Phase 3 (Subphases 3.1 & 3.2: Stateful Login Macro Engine & Active Keep-Alive Loop)
Remediation Design  : 
                      1. Semantic Action Blacklist: Extend `pkg/crawler/browser/monkey.go` to explicitly
                         reject elements containing "logout", "signout", "exit", "disconnect", "invalidate".
                      2. Session Canary Polling: Register an active session health check URL (e.g. `/api/whoami`).
                         Every 10 interaction steps, poll the canary. If HTTP 401/403 or login redirect occurs,
                         pause the crawler, trigger the Phase 3 login macro to obtain a fresh token, update
                         `localStorage`/cookies, and resume crawl seamlessly.
Testing Verification:
- Designated Target : `C:\SecurityLabs\webgoat` (Port 8080 - Spring Boot session keep-alive) &
                      `C:\SecurityLabs\juice-shop` (Port 3000 - authenticated session `jim@juice-sh.op`).
- Testing Procedure : Crawl Juice Shop while logged in. Simulate intentional token revocation or force a
                      logout trigger; assert that the crawler detects session loss, automatically executes

                      100% authenticated route continuity.

[L1.3] Closed Shadow DOM & Canvas/WebGL Virtual DOM Traversal Blindspot
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/monkey.go` (DOM Selector Engine)
Current Behavior    : Evaluates interactive targets using standard DOM query selectors:
                      `document.querySelectorAll('a, button, input, select, textarea, [onclick]')`.

                      elements from the standard DOM tree.

                      applications appear completely empty. FELIX discovers 0 interactive elements, missing

Remediation Design  : 
                      1. Use CDP `DOM.describeNode` with `pierce: true` and `DOM.resolveNode` to inspect
                         closed shadow roots directly from the Chrome engine level, bypassing JavaScript
                         DOM boundary protections.
                      2. For canvas-based apps, implement visual coordinate OCR and layout heuristic grid
                         clicking to interact with canvas-drawn controls.

[L1.4] Infinite Feeds, Calendar Traps & Boundless SPA State Graph Explosions
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/spa.go` (SPA State Transition Engine)
Current Behavior    : Records explored states using URL paths/hashes and a structural DOM hash.
The Limitation      : Modern applications frequently include unbounded dynamic content generators:
                      - Infinite scroll feeds (e.g. social posts, product review feeds loading page 1..N).
                      - Interactive date pickers / calendars (generating endless `/#/events?date=YYYY-MM-DD`).
                      - Dynamically sorted tables with infinite permutation parameters (`?sort=asc&col=1`).
                      FELIX tracks these as new distinct states, causing exponential state explosions.
Upstream Impact     : In Phase 2 parameter fuzzing and Phase 8 large-scale scanning, the crawler enters
                      an infinite discovery loop. It burns through the safety request quota (MaxRequestsPerTarget),
                      allocates gigabytes of state data in memory, and stalls scans for hours while probing
                      structurally identical pagination screens.
Planned Fix Phase   : Subphase 2.6 / 1.6+ (Structural DOM Clustering & State Equivalence Hashing)
Remediation Design  : Implement DOM Skeleton Normalization:
                      - Strip dynamic text, numeric IDs, and timestamps before computing the state signature.
                      - If 3 consecutive states share an identical DOM skeleton with only list-item pagination
                        or query string date permutations, classify the view as an "Infinite Feed Pattern".
                      - Cap pagination exploration to a configurable threshold (e.g. MaxPaginationDepth = 3)
                        and prune subsequent permutations from the state graph.
Testing Verification:
- Designated Target : `C:\SecurityLabs\juice-shop` (Port 3000 - infinite review pagination) &
                      `C:\SecurityLabs\wackopicko` (Port 8085 - pagination catalog).
- Testing Procedure : Direct crawler to Juice Shop reviews or WackoPicko catalog; verify crawler caps

[L1.5] High-Concurrency Memory Consumption (OS Process Bloat vs. Context Pooling)
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/launcher.go` (Process Management)
Current Behavior    : Spawns an isolated OS-level browser process (`msedge.exe`/`chrome.exe`) per instance
                      with its own temporary `--user-data-dir`.
The Limitation      : Each Chromium OS process tree (main process + GPU process + network service + renderers)
                      consumes between 80 MB and 150 MB of resident RAM. Launching 10 parallel browser sessions
                      consumes ~1.5 GB of RAM.
Upstream Impact     : In Phase 8 (Fleet-Scale Autonomous Auditing), FELIX is designed to audit dozens of
                      microservices simultaneously. Launching 50 to 100 concurrent browser processes would demand
                      8 GB to 15 GB of RAM, causing intense Windows memory paging, disk thrashing, high latency,
                      or OS Out-Of-Memory (OOM) crashes.
Planned Fix Phase   : Phase 8.1 (Lightweight Target Context Multiplexing via CDP `Target.createBrowserContext`)
Remediation Design  : Maintain a persistent, warm Chromium daemon process. Instead of spawning new OS processes
                      for concurrent workers, invoke CDP `Target.createBrowserContext`. Each browser context provides
                      complete cookie, cache, and storage isolation with zero OS process overhead, reducing memory
                      consumption from ~120 MB down to ~15 MB per concurrent session (>85% memory reduction).
Testing Verification:
- Designated Target : Stress benchmark against `C:\SecurityLabs\juice-shop` (Port 3000) under 50 concurrent sessions.
- Testing Procedure : Run launcher benchmark spawning 50 parallel crawling sessions concurrently using BrowserContext
                      multiplexing; track total RAM usage via Windows Performance Counters.
- Pass Exit Metric  : 50 concurrent sessions complete with total memory footprint < 1.8 GB (vs >7 GB previously);
                      zero zombie processes and 0 crashed workers.

[L1.6] WebSockets & Server-Sent Events (SSE) Bidirectional State Fuzzing Blindspot
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/network.go` (CDP Network Sniffer)
Current Behavior    : Sniffs and logs HTTP/HTTPS fetch and XHR requests. For WebSockets, it observes the
                      HTTP 101 Switching Protocols handshake, but ignores subsequent bi-directional frames.
The Limitation      : Modern interactive web applications (real-time chat, collaborative documents, live financial
                      trading systems) execute business logic and data exchanges over WebSocket message frames
                      (`ws://` and `wss://`) or Server-Sent Events (`text/event-stream`).
                      FELIX does not capture, catalog, or manipulate the contents of individual WS frames.
Upstream Impact     : In Phase 2, the Active Parameter Fuzzer operates strictly over HTTP request parameters.
                      Any application parameter transmitted over a live WebSocket connection is completely
                      invisible and immune to fuzzing. SQL injection, command injection, or authorization bypasses
                      residing in WebSocket handlers cannot be discovered.
Planned Fix Phase   : Phase 2.7 / Phase 8.4 (CDP WebSocket Frame Interceptor & Message Tampering Engine)
Remediation Design  : Enable CDP `Network.webSocketFrameReceived` and `Network.webSocketFrameSent` listeners.
                      - Parse JSON-RPC, text, and binary message frames into the parameter cataloger.
                      - Implement active message injection via CDP `Network.sendWebSocketMessage` to fuzz
                        WebSocket parameters with Phase 2 injection payloads.
Testing Verification:

- Testing Procedure : Connect crawler to DVWS WebSocket chat service; intercept outgoing message frames;

[L1.8] Cross-Origin iframe Isolation & Sandboxed CSP Hooking Boundary
----------------------------------------------------------------------------------------------------
Subsystem Component : `pkg/crawler/browser/dom_xss.go`, `pkg/crawler/browser/storage.go`
Current Behavior    : Injects DOM XSS instrumentation hooks via `Page.addScriptToEvaluateOnNewDocument`.
The Limitation      : When a web page embeds third-party frames from different domains or subdomains
                      (e.g., payment portals, third-party authentication widgets) or iframes with strict
                      `sandbox` attributes, Chromium enforces Cross-Origin Isolation (Site Isolation).
                      Hooks injected at the top-level page do not automatically propagate into child frames
                      running in isolated renderer processes.
Upstream Impact     : In Phase 2 active fuzzing and Phase 8 compliance testing, vulnerable DOM sinks
                      (e.g., `window.addEventListener('message', ...)`) and client secrets residing inside
                      embedded cross-origin iframes are completely hidden from FELIX.
Planned Fix Phase   : Subphase 1.4+ / Phase 8 (CDP `Target.setAutoAttach` Frame Hierarchy Engine)
Remediation Design  : Enable CDP `Target.setAutoAttach` with `autoAttach: true` and `waitForDebuggerOnStart: false`.
                      When child iframes or web workers are spawned, Chromium notifies FELIX via target
                      events, allowing FELIX to attach to child sessions and inject DOM XSS hooks into every
                      individual execution frame.
Testing Verification:
- Designated Target : Synthetic Cross-Origin Fixture `test/lab/cross_origin_frame.html` &
                      `C:\SecurityLabs\secure-coding-dojo` (Port 4005).
- Testing Procedure : Load parent page embedding cross-origin iframe with vulnerable DOM sink; verify
                      FELIX attaches to child target and traps unescaped canary payloads executed within iframe.
- Pass Exit Metric  : 100% sink detection across both parent and child iframe renderer contexts.

----------------------------------------------------------------------------------------------------
Status              : [RESOLVED IN SUBPHASE 2.2]
Subsystem Target    : `pkg/fuzzer/sqli.go`, `pkg/apisec/differential.go`

[L2.2] Downstream Concurrency-Induced Latency False Positives in Time-Based SQLi
----------------------------------------------------------------------------------------------------
Status              : [RESOLVED IN SUBPHASE 2.2]
Subsystem Target    : `pkg/fuzzer/sqli.go`
The Limitation      : Injecting time-based blind payloads (`SLEEP(5)` or `pg_sleep(5)`) while executing
                      parallel scanner threads causes server-side CPU queuing, causing normal requests to
                      take >5000ms and producing false positive SQL injection findings.
Upstream Impact     : Fails verification in CI/CD pipelines under concurrent testing load.
Resolution Impl     : Implemented `AnalyzeTimeBased` with sequential mathematical latency progression:
                      `1s` probe -> `3s` probe -> `0s` control probe, asserting linear scaling (T(3s)-T(1s) >= 1500ms)
                      and control baseline return (T(0s) <= baseline + 500ms). Rejects queuing jitter.
Testing Website/Lab : `C:\SecurityLabs\nodegoat` (Port 4000 - Server-Side JS Injection & Mongo Latency).
Testing Procedure   : When an initial latency spike is detected, execute a strict 3-step verification progression:
                      Step 1: Test with Delay = 1s (assert elapsed >= 850ms).
                      Step 2: Test with Delay = 3s (assert elapsed >= 2500ms, Delta >= 1500ms).
                      Step 3: Test with Delay = 0s control probe (assert elapsed <= baseline + 500ms).
Verification Command: `go test -v -count=1 ./pkg/fuzzer -run TestTimeBasedLatencyProgression_LinearScaling`
Evidence Receipt    : `test/evidence/phase2/2.2_sqli_differential_proof.json`
Pass Exit Metric    : Zero false positive time-based findings under parallel multi-threaded load.

[L2.4] Target Rate-Limiter Exhaustion & WAF IP Ban Without Adaptive Backoff
----------------------------------------------------------------------------------------------------
Status              : [RESOLVED IN SUBPHASE 2.6]
Subsystem Target    : pkg/fuzzer/pool.go
The Limitation      : Fuzzing target applications at full unbounded concurrency exhausts target connection pools,
                      triggers HTTP 429 Too Many Requests rate-limiting, and can lead to WAF IP bans or dropped
                      requests without adaptive backoff and concurrency control.
Upstream Impact     : Fuzzing campaigns drop requests, corrupt test integrity, or get banned during live audits.
Resolution Impl     : Implemented FuzzingPool and AdaptiveRateLimitedTransport with dynamic concurrency slot permits,
                      lock-free rate pacing, exponential AIMD backoff on HTTP 429 / connection drops, MaxBackoff-capped
                      Retry-After parsing (integer & HTTP-date), request-body replay across retries, panic-free shutdown
                      synchronization, dial-time SSRF metadata protection, and additive recovery upon consecutive successes.
Testing Website/Lab : C:\SecurityLabs\webgoat (Port 8082 / 8080) & Local Rate Limiter Mock (test/lab/rate_limit_mock).
Testing Procedure   : Dispatch 500 fuzzing requests through worker pool with 25 concurrent goroutines; simulate target
                      returning HTTP 429; assert rate limiter dynamically backs off, halves concurrency, retries throttled
                      requests, and recovers without dropping requests.
Verification Command: go test -v -count=1 ./pkg/fuzzer -run TestBenchmark_FuzzingConcurrencyAndAdaptiveRateLimiter
Evidence Receipt    : test/evidence/phase2/2.6_rate_limiter_recovery_proof.json
Supplemental Receipt: test/evidence/phase2/2.6_rate_limiter_correctness_proof.json
Pass Exit Metric    : 0 lost requests; 0 unhandled connection dropouts; throughput >100 req/s on loopback.
Remaining Boundaries: 1. Live target WebGoat does not throttle login route; 429 backoff is proven via local HTTP testbed.
                      2. Cloud metadata SSRF guard blocks literal IP/IPv6, link-local 169.254.0.0/16, well-known hostnames,
                         DNS rebinding at DialContext, and redirects; external reverse proxy SSRF requires Phase 5 auditing.
                      3. Host Windows OS lacks Cgo/GCC compiler, precluding dynamic -race execution.
